# Техническое задание
## Прототип: ИИ-агент для выявления жизненной цели, целеполагания и коучинга (без аутентификации)

Версия: 0.1 (прототип)
Дата: 28.07.2026

---

## 1. Назначение и границы прототипа

Прототип демонстрирует полный цикл: интервью → синтез профиля (Икигай) → выявление
противоречий/саботажа → прояснение потребности → работа с тремя+ областями жизни →
стратегические пути → SMART/OKR-цель → план → еженедельный трекинг.

**Вне границ прототипа** (переносится в следующие фазы):
- полноценная аутентификация (OAuth, email-подтверждение)
- платёжный флоу целиком (booking делает заглушку/форму интереса, без реальной оплаты)
- мобильное приложение / Telegram-бот
- дашборд для коуча (мультитенантность)
- vector DB для нишевых методик (метод Толстых и т.п.) — оставляем точку расширения

---

## 2. Идентификация пользователя без аутентификации

Т.к. полноценной авторизации нет, а нужна персистентность между визитами:

```
1. При первом визите: генерируется client_uuid (crypto.randomUUID())
   и сохраняется в localStorage браузера.
2. Агент в начале диалога спрашивает имя — оно используется ТОЛЬКО
   для персонализации обращения в диалоге, не как идентификатор.
3. Все данные в БД привязаны к client_uuid, а не к имени.
4. Имя хранится как поле profile_snapshots.display_name.
```

**Ограничение (зафиксировать явно для стейкхолдеров):** очистка localStorage или
смена браузера/устройства = потеря доступа к профилю. Это осознанный компромисс
прототипа, не для продакшена. В UI показать предупреждение: *"Твой прогресс
привязан к этому браузеру. Введи email, чтобы не потерять данные"* — email
опционально можно собирать уже сейчас как задел под будущий auth (magic link),
не реализуя сам auth-флоу.

## 3. Маршрутизация в начале диалога (intent_router_agent)

Первый шаг любого взаимодействия — **не анкета**, а определение того, зачем
человек вообще пришёл. Три сценария принципиально разные по флоу и не должны
смешиваться в один and тот же путь.

```
intent_router_agent (первый агент, до всего остального)
   → задаёт открытый вопрос + 3 варианта-подсказки (кнопки в UI)
   → классифицирует ответ (свободный текст ИЛИ явный выбор кнопки)
        ↓
   ┌────────────────┬─────────────────────┬──────────────────────┐
   │   Путь A        │   Путь B            │   Путь C              │
   │ поиск идеи      │ конкретная проблема │ анализ/наладка        │
   │ предназначения  │ в жизни/проекте     │ доменов жизни          │
   └────────────────┴─────────────────────┴──────────────────────┘
```

### 3.1  главное меню на стартовой странице

```
"Расскажи, что привело тебя сюда сегодня — выбери, что ближе, или опиши своими словами:

  [1] последняя сессия
  [2] хочу поработать с одной из моих целей 
  [3] Ищу своё призвание, идеи которые меня зажгут — анкета для поиска настоящего призвания по биографии

  [4] У меня повторяется дискомфорт в конкретной области жизни,
      хочу разобраться и найти решение

  [5] Хочу проверить и наладить конкретные области жизни
      (отношения, деньги, здоровье, самореализация и т.д.)"
```

Если пользователь отвечает свободным текстом, а не кнопкой — `intent_router_agent`
классифицирует через LLM в один из трёх путей и переспрашивает подтверждение
("правильно понимаю, что ты ищешь...?") прежде чем ветвиться — чтобы не увести
человека не в ту ветку по ошибочной классификации.

[1] - загружает контекст последней сессии, пишет короткое резюме последней сессии, отображает поле для ввода текста и общается с пользователем в режиме диалога

[2] - переход на страницу со списком целей

Под плашкой каждой цели есть кнопки: 1) анализ готовности и саботажа 2) стратегия и тактика  
 клик по 1) `synthesis_agent` → `tension_resolution_agent`
 клик по 2) - `goal_agent` → `plan_agent`



[3] - interview_agent (см. п. 3.2)
[4] - п. 3.3
[5] - п. 3.4

### 3.3 Путь B — конкретная проблема в жизни/проекте

Новый агент `problem_diagnosis_agent` — **не анкета из фиксированных вопросов**,
а мягкий разговорный флоу, идущий по существу проблемы, а не по чек-листу:

```
problem_diagnosis_agent:
  1. мягко и ненавязчиво расспрашивает про точку А (что происходит сейчас,
     в чём именно проблема, своими словами человека)
  2. расспрашивает про точку Б (как выглядело бы решение/желаемый результат)
  3. уточняет формулировку сути проблемы (не додумывает за пользователя —
     переспрашивает, если неясно)
  4. предлагает выбор:
       a) бесплатная диагностика/разбор прямо в чате
       b) запись на личную консультацию/сессию с человеком
       c) не сейчас
```

Если в ходе разговора всплывает, что проблема относится к одному из 6 доменов
(деньги/отношения/здоровье/...) — управление плавно передаётся в
`domain_module_agent` (раздел 7) с уже накопленным контекстом, не начиная
заново с нуля.

Если возникает основание для полноценной цели с горизонтом (человек хочет не
просто "разобраться", а действительно что-то изменить/построить) —
`problem_diagnosis_agent` предлагает продолжить в `goal_agent`, минуя
интервью Пути A (то есть Путь B может "перетекать" в целеполагание без
полной анкеты — она не всегда нужна, если точка А/Б уже прояснены в разговоре).

### 3.4 Путь C — анализ и наладка доменов жизни

Двухступенчатый процесс: сначала **короткий скрининг по всем доменам**, потом
**подробный опросник только по выбранным**.

```
Шаг 1: domain_screening_agent
   → 2-3 коротких вопроса на КАЖДЫЙ из 6 доменов (relationships, money,
     health, purpose, safety, belonging) — быстрый скан, не глубокий разбор
   → по ответам подсвечивает, где похоже на проблему (эвристика по
     ключевым словам + LLM-классификация тона/содержания ответа)
        ↓
Шаг 2: пользователю показывается список доменов с пометкой
   "похоже, есть над чем поработать" — пользователь ВЫБИРАЕТ,
   с какими доменами работать дальше (multi-select), необязательно
   со всеми подсвеченными
        ↓
Шаг 3: domain_deep_questionnaire_agent — для КАЖДОГО выбранного домена
   отдельно, подробный опросник, построенный на основе конфигурируемого
   списка популярных ограничивающих убеждений для этого домена
   (контент списка предоставляется заказчиком отдельно, см. открытые
   вопросы, раздел 12)
        ↓
Шаг 4: signal_detector — анализирует ответы подробного опросника,
   ищет явные признаки:
   - самосаботаж, прокрастинация
   - конкретные страхи/фобии
   - проблемные/токсичные отношения, зависимые (созависимые) отношения
   - синдром спасателя, синдром самозванца
   - эмоциональный дискомфорт от повторяющихся ситуаций
   - зависимость от еды/веществ
        ↓
Шаг 5: ЕСЛИ обнаружен хотя бы один сигнал —
   domain_module_agent предлагает тот же выбор, что и раньше (раздел 7.1):
   бесплатная КПТ-диагностика в чате ИЛИ запись на личную сессию.
   ЕСЛИ сигналов нет — домен просто помечается как "проработан",
   без принудительного предложения терапии.
```

**Важное ограничение (safety):** список ограничивающих убеждений используется
только как основа для ФОРМУЛИРОВКИ вопросов опросника, не для того, чтобы
`domain_deep_questionnaire_agent` сам ставил диагнозы по ключевым словам ("если
ответ похож на убеждение X — значит у человека проблема Y"). Итоговое решение о
том, есть ли реальный сигнал, делает `signal_detector` на основе смысла ответа
целиком, а не факта совпадения с формулировкой убеждения — иначе высок риск
ложных срабатываний на нейтральных ответах.

                       -- substance_food_addiction|emotional_discomfort_repeated
  evidence JSONB,
  confidence FLOAT,
  created_at TIMESTAMPTZ DEFAULT now()
);

## 4. Структура анкеты интервью (interview_agent)

Итоговая структура — **6 тематических блоков**, блок 4 условный (показывается не
всем). Внутри блока агент ведёт адаптивный диалог (не обязательно все вопросы
блока подряд текстом — часть служит "затравкой", если ответ пользователя уже
покрыл несколько пунктов сразу, агент их не дублирует).

| Блок | Название | Кол-во вопросов | Условие показа |
|---|---|---|---|
| 1 | Кто ты (разогрев и контекст) | 10 | всегда |
| 2 | Что бесит (боли и раздражения) | 15 | всегда |
| 3 | Костыли (workarounds и самопальные решения) | 15 | всегда |
| 4 | Переход (крупное изменение) | 15 | **условно**, см. 4.1 |
| 5 | Экспертиза (где ты знаешь больше других) | 10 | всегда |
| 6 | Проверка (закрытие и валидация) | **5** из 15 (см. 4.2) | всегда |

### 4.1 Условие показа блока 4 ("Переход")

Перед блоком 4 (после блока 3) `interview_agent` задаёт один скрининг-вопрос:

```
"За последние 12 месяцев у тебя было существенное изменение в жизни —
 переезд, смена семейного статуса, значимая потеря или внезапный рост
 (в доходе, статусе, обстоятельствах)?"
```

```
IF ответ положительный (да/опиши что):
   → показать блок 4 целиком (15 вопросов, адаптивно)
ELSE:
   → пропустить блок 4, перейти сразу к блоку 5
```

Технически: результат скрининга пишется в поле `interview_sessions.block4_triggered
(boolean)` и `block4_trigger_description (text)` — это же поле позже может
использоваться `tension_resolution_agent`/`self_sabotage_detector` как
дополнительный сигнал (недавнее большое изменение — релевантный контекст для
интерпретации текущих противоречий).

### 4.2 Урезанный блок 6 ("Проверка")

Из 15 стандартных вопросов блока 6 в прототипе используются только **5**, в
следующем порядке предъявления пользователю: **12, 1, 2, 3, 4** (не 1-2-3-4-12).
Смысл порядка: сначала дать человеку назвать недооценённую идею (вопрос 12),
и только потом переходить к обычной валидации по классической воронке
(что взбудоражило → готовность платить → пробовал ли решить → сколько уходит
денег/времени).

```
block_6.questions = [
  { order: 1, source_index: 12, text: "Какая из идей в твоей голове сейчас кажется самой недооценённой?" },
  { order: 2, source_index: 1,  text: "Какая из обсуждённых тем взбудоражила тебя больше всего?" },
  { order: 3, source_index: 2,  text: "Какую из обсуждённых проблем ты бы оплатил решением прямо сегодня? Сколько готов отдать?" },
  { order: 4, source_index: 3,  text: "Когда последний раз пытался найти решение этой проблемы? Что искал и где?" },
  { order: 5, source_index: 4,  text: "Сколько денег и времени уходит на эту проблему в месяц?" }
]
```

Остальные 10 вопросов блока 6 (5, 6, 7, 8, 9, 10, 11, 13, 14, 15 по исходной
нумерации) в прототипе не используются — при необходимости конфигурация
позволяет включить их позже без изменения кода (см. таблицу `interview_config`
ниже).

### 4.3 Хранение конфигурации анкеты (чтобы блоки/вопросы не были захардкожены)

```sql
CREATE TABLE interview_config (
  id UUID PRIMARY KEY,
  block_number INT,
  block_name TEXT,
  is_conditional BOOLEAN DEFAULT false,
  trigger_question TEXT,          -- для блока 4
  questions JSONB,                -- [{order, source_index, text}]
  active BOOLEAN DEFAULT true
);

CREATE TABLE interview_sessions (
  id UUID PRIMARY KEY,
  client_uuid UUID REFERENCES clients(client_uuid),
  current_block INT,
  block4_triggered BOOLEAN,
  block4_trigger_description TEXT,
  answers JSONB,                  -- {block_number: {question_order: answer_text}}
  status TEXT DEFAULT 'in_progress',  -- in_progress|completed
  created_at TIMESTAMPTZ DEFAULT now()
);
```

Такое разделение (конфиг вопросов отдельно от кода агента) позволяет менять
состав блоков/вопросов без деплоя — важно, т.к. набор вопросов уже один раз
менялся в ходе обсуждения ТЗ и наверняка будет меняться ещё.

## 6. Цепочка агентов (полный пайплайн)

```
0. intent_router_agent      — ПЕРВЫЙ агент в любом диалоге, определяет путь
                              A/B/C (см. раздел 3), только после этого
                              запускается соответствующая ветка
1. interview_agent          — адаптивное интервью, 6 блоков (блок 4 условный,
                              блок 6 урезан) — см. раздел 4 [только путь A]
2. synthesis_agent          — Икигай-профиль + tension_flags
3. tension_resolution_agent — предъявляет противоречие, ждёт подтверждения
4. self_sabotage_detector   — правило (не LLM), сканирует паттерны в 2+ сферах
5. self_sabotage_agent      — Opus 4.8, разбор саботажа, маршрутизация в КПТ/платно
6. cbt_session_agent        — Sonnet 5, бесплатная КПТ-сессия, эскалация при кризисе
7. need_deconstruction_agent— laddering-диалог "для чего тебе это"
8. domain_module_agent      — универсальный, конфигурируется под 6 областей жизни
9. strategy_agent           — веер стратегических путей к точке Б
10. goal_agent              — SMART/OKR из выбранного пути
11. goal_capacity_agent     — CROSS-CUTTING: при обнаружении новой (в т.ч.
                              промежуточной) цели решает parallel/sequential,
                              см. раздел 7.4
12. plan_agent              — декомпозиция год→месяц→неделя (учитывает
                              активные/приостановленные цели клиента)
13. checkin_agent           — еженедельный разбор прогресса по ВСЕМ активным целям
14. reflection_agent        — ежемесячная конденсация в profile_snapshot
```

**Агенты, специфичные для путей B и C** (запускаются вместо/до пункта 1,
не после интервью):

```
15. problem_diagnosis_agent      — Путь B: разговорный разбор точка А/точка Б/
                                    суть проблемы, см. раздел 3.3
16. domain_screening_agent       — Путь C, шаг 1: короткий скан всех 6 доменов,
                                    см. раздел 3.4
17. domain_deep_questionnaire_agent — Путь C, шаг 3: подробный опросник по
                                    выбранным доменам на основе конфигурируемых
                                    ограничивающих убеждений
18. signal_detector              — Путь C, шаг 4: правило + LLM-классификация,
                                    ищет сигналы саботажа/зависимостей/фобий/
                                    созависимости и т.п., см. раздел 3.4
```

Персона "друг-советчик, вторая голова" — общий стилевой слой (system prompt
fragment), подключаемый к агентам 0, 3, 5, 6, 7, 8, 9, 11, 15, 16, 17 (все, что
говорят с человеком напрямую в чувствительных темах или просят его выбор).
Агенты 2, 4, 12, 14, 18 работают "за кулисами" со структурой данных без
прямого диалога.

**Важно:** `goal_capacity_agent` — не отдельный шаг в конце пайплайна, а
триггер, который может сработать в ЛЮБОЙ момент любого диалога (interview,
cbt_session, need_deconstruction, domain_module, skill_coach) — как только
в разговоре опознаётся новая цель/подцель (навык, ограничение для проработки
и т.п.), не заявленная явно ранее. Это верно для всех трёх путей, не только A.

## 7. Универсальный модуль домена (relationships / money / health / purpose / safety / belonging)

Вместо 5+ отдельных агентов — один `domain_module_agent`, параметризуемый конфигом:

```json
{
  "domain": "money",
  "display_name": "Деньги и доход",
  "detection_keywords": ["денег не хватает", "нет дохода", "боюсь брать оплату", "..."],
  "free_option": {
    "type": "cbt_chat",
    "agent_ref": "cbt_session_agent",
    "topic_scope": "денежные установки"
  },
  "paid_option": {
    "type": "human_session",
    "method_name": "метод Толстых",
    "booking_target": "calendly_money_track"
  },
  "special_flow": "money_mindset_choice"  // см. п.7.3 ниже
}
```

### 7.1 Алгоритм (общий для всех доменов)

```
domain_module_agent обнаруживает проблему в области X (по ключевым словам
  ИЛИ по LLM-классификации свободного текста интервью/check-in)
        ↓
Шаг 1: мягко озвучить проблематику, ОПИРАЯСЬ НА СЛОВА ПОЛЬЗОВАТЕЛЯ (цитаты)
        ↓
Шаг 2: предложить выбор:
  a) бесплатная диагностика/терапия через чат (cbt_session_agent, scope=X)
  b) запись на консультацию с человеком (booking form)
  c) не сейчас
        ↓
domain_flags.status обновляется соответственно
```

### 7.2 Специфика для целей со сроком ≥ 6 месяцев

```
IF goal.horizon_months >= 6:
   goal_agent (после формирования цели) спрашивает:
   "Для такой цели можно использовать НЛП-методику постановки/сопровождения
    (отдельный специализированный агент/метод) — или пойти по обычному
    плану от текущей модели. Что выбираешь?"
        ↓
   choice = 'nlp_method' → создаётся nlp_track_session (заглушка в прототипе:
             фиксированная последовательность вопросов по методике,
             контент методики — TBD, предоставляется отдельно заказчиком)
   choice = 'standard_ai_plan' → обычный plan_agent, без изменений
```

### 7.3 Специфика для домена "money", когда деньги — часть решения точки Б

Отдельное правило, срабатывает НЕ только внутри модуля money, а также когда
`strategy_agent`/`goal_agent` определяют деньги как необходимое условие для
точки Б в ЛЮБОЙ другой цели:

```
IF goal.requires_money_as_prerequisite == true:
   агент озвучивает: "Часть пути к цели X — это [нехватка дохода/заработок].
   Хочешь проработать денежные установки отдельным шагом (по методике,
   она будет дана отдельно) — или чтобы я сразу дал рекомендации по
   практическому решению (как обсуждали ранее — стратегии дохода)?"
        ↓
   choice = 'money_mindset_track' → domain_module_agent(domain=money), п.7.1
   choice = 'ai_recommendations'  → strategy_agent генерирует практические
                                     пути заработка (не психологическая работа)
```

### 7.4 Множественные цели и приоритизация (goal_capacity_agent)

Пользователь ведёт **несколько активных целей одновременно** (например: "выучить
навык для работы" + "наладить отношения" + "разобраться с деньгами"). В ходе
диагностики/бесед (интервью, КПТ-сессия, need-деконструкция, работа с доменом,
skill-коучинг) может всплыть **новая цель, не заявленная изначально** — чаще
всего промежуточная (выучить конкретный навык, проработать конкретное
ограничение, которое блокирует основную цель).

**Алгоритм срабатывания:**

```
Новая цель/подцель обнаружена в диалоге любого агента
        ↓
goal_capacity_agent оценивает:
  1. Список текущих активных goals клиента (status='active') + их
     фактическая недельная нагрузка (сумма среднего кол-ва plan_items
     за последние N недель)
  2. Тип связи новой цели с существующими:
     - blocking: без неё существующие цели физически не продвинуть
       (например: цель "сменить профессию" требует навыка X,
       без которого следующие шаги плана невозможны)
     - independent: может вестись параллельно без конфликта ресурсов
     - resource_conflict: технически независима, но суммарная нагрузка
       (время/энергия) превышает реалистичный лимit пользователя
  3. Оценка нагрузки строится на данных profile.constraints (сколько
     времени реально есть) + история check_ins (% выполнения плана
     за последние недели — если уже отстаёт, это сигнал против
     добавления ещё одной параллельной цели)
        ↓
Агент НЕ решает сам — предъявляет вывод пользователю и спрашивает:
   "Смотрю, что цель '[новая]' [блокирует / не блокирует] движение
    по остальным. При твоей текущей загрузке [коротко: % выполнения
    последних недель] — как лучше: вести её параллельно со всем
    остальным, или сделать приоритетной и поставить другие цели
    на паузу, пока не закроешь эту?"
        ↓
Варианты ответа пользователя:
   - 'parallel'            → новая цель создаётся как goals(execution_mode=
                              'parallel'), остальные без изменений
   - 'prioritize_new'       → новая цель execution_mode='sequential_priority',
                              остальные активные цели → status='paused',
                              paused_reason='ожидает завершения: <goal_id>'
   - 'keep_existing_priority' → новая цель создаётся, но сама ставится
                              в status='paused' до момента, который
                              укажет пользователь, или до ближайшего
                              ежемесячного пересмотра (reflection_agent)
```

**Важно:** приостановленные (`paused`) цели не удаляются и не забываются —
`plan_agent` просто не генерирует по ним задачи на текущую неделю, а
`reflection_agent` при ежемесячной конденсации проверяет, не пора ли
вернуть какую-то из них в `active` (например, если приоритетная цель
достигнута или сама встала на паузу).

## 8. Схема БД (прототип — без auth-таблиц)

```sql
-- Идентификация без auth
CREATE TABLE clients (
  client_uuid UUID PRIMARY KEY,      -- из localStorage
  display_name TEXT,
  email TEXT,                        -- опционально, задел под будущий auth
  created_at TIMESTAMPTZ DEFAULT now()
);

-- Профиль (версионируемый)
CREATE TABLE profile_snapshots (
  id UUID PRIMARY KEY,
  client_uuid UUID REFERENCES clients(client_uuid),
  version INT,
  data JSONB,             -- values, constraints, skills, ikigai_map, dreams
  source TEXT,            -- initial_interview | checkin_update | reflection
  created_at TIMESTAMPTZ DEFAULT now()
);

-- Противоречия / саботаж
CREATE TABLE tension_flags (
  id UUID PRIMARY KEY,
  client_uuid UUID REFERENCES clients(client_uuid),
  type TEXT,              -- dream_vs_behavior_pattern | recurring_pattern | ...
  description TEXT,
  evidence JSONB,
  confidence FLOAT,
  status TEXT DEFAULT 'detected'  -- detected|user_confirmed|dismissed
);

CREATE TABLE self_sabotage_flags (
  id UUID PRIMARY KEY,
  client_uuid UUID REFERENCES clients(client_uuid),
  pattern_description TEXT,
  domains JSONB,
  evidence_refs JSONB,
  status TEXT DEFAULT 'detected'  -- detected|user_acknowledged|in_cbt_session|escalated_to_paid|dismissed
);

CREATE TABLE cbt_sessions (
  id UUID PRIMARY KEY,
  client_uuid UUID REFERENCES clients(client_uuid),
  related_flag_id UUID,           -- self_sabotage_flags.id ИЛИ domain_flags.id
  domain TEXT,                    -- 'sabotage' | 'money' | 'relationships' | 'health' | ...
  session_log JSONB,
  outcome TEXT,                   -- resolved|needs_followup|escalated
  model_used TEXT,
  created_at TIMESTAMPTZ DEFAULT now()
);

-- Прояснение потребности
CREATE TABLE need_analyses (
  id UUID PRIMARY KEY,
  client_uuid UUID REFERENCES clients(client_uuid),
  goal_id UUID,
  stated_goal TEXT,
  laddering_chain JSONB,
  underlying_needs JSONB,   -- [{category, description, confidence}]
  created_at TIMESTAMPTZ DEFAULT now()
);

-- Домены жизни (универсальная таблица под конфигурируемый модуль)
CREATE TABLE domain_flags (
  id UUID PRIMARY KEY,
  client_uuid UUID REFERENCES clients(client_uuid),
  domain TEXT,             -- money|relationships|health|purpose|safety|belonging
  description TEXT,
  evidence JSONB,
  status TEXT DEFAULT 'detected',  -- detected|free_chat_chosen|paid_booked|dismissed
  created_at TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE booking_requests (
  id UUID PRIMARY KEY,
  client_uuid UUID REFERENCES clients(client_uuid),
  domain TEXT,
  method_name TEXT,        -- 'метод Толстых' и т.п.
  contact_info TEXT,       -- т.к. нет auth — email/телефон вводится вручную
  status TEXT DEFAULT 'requested',
  created_at TIMESTAMPTZ DEFAULT now()
);

-- Цели и планы (пользователь может вести НЕСКОЛЬКО активных goals одновременно)
CREATE TABLE goals (
  id UUID PRIMARY KEY,
  client_uuid UUID REFERENCES clients(client_uuid),
  title TEXT,
  horizon TEXT,             -- 5y|3y|1y
  horizon_months INT,
  smart_json JSONB,
  requires_money_as_prerequisite BOOLEAN DEFAULT false,
  planning_track TEXT,      -- 'standard_ai_plan' | 'nlp_method'
  origin TEXT DEFAULT 'primary',      -- 'primary' | 'emergent' (всплыла в ходе диагностики)
  blocks_goal_ids JSONB,               -- [goal_id, ...] какие цели эта блокирует, если blocking
  execution_mode TEXT,                 -- 'parallel' | 'sequential_priority' | NULL (для primary)
  status TEXT DEFAULT 'active',        -- active|paused|achieved|abandoned
  paused_reason TEXT,                  -- напр. 'ожидает завершения: <goal_id>'
  created_at TIMESTAMPTZ DEFAULT now()
);

-- Лог решений goal_capacity_agent — для прозрачности и для reflection_agent,
-- который проверяет, не пора ли вернуть paused-цель в active
CREATE TABLE goal_capacity_decisions (
  id UUID PRIMARY KEY,
  client_uuid UUID REFERENCES clients(client_uuid),
  new_goal_id UUID REFERENCES goals(id),
  relation_type TEXT,        -- blocking | independent | resource_conflict
  workload_snapshot JSONB,   -- % выполнения плана за последние недели на момент решения
  user_choice TEXT,          -- parallel | prioritize_new | keep_existing_priority
  affected_goal_ids JSONB,   -- какие goals были поставлены на паузу этим решением
  created_at TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE okrs (
  id UUID PRIMARY KEY,
  goal_id UUID REFERENCES goals(id),
  objective TEXT,
  key_results JSONB,
  period TEXT
);

CREATE TABLE plan_items (
  id UUID PRIMARY KEY,
  client_uuid UUID REFERENCES clients(client_uuid),
  okr_id UUID REFERENCES okrs(id),
  period_type TEXT,         -- month|week
  period_key TEXT,
  task TEXT,
  status TEXT DEFAULT 'pending'
);

CREATE TABLE check_ins (
  id UUID PRIMARY KEY,
  client_uuid UUID REFERENCES clients(client_uuid),
  period_key TEXT,
  raw_input TEXT,
  ai_analysis JSONB,
  plan_adjustment JSONB,
  created_at TIMESTAMPTZ DEFAULT now()
);
```

## 11. Нефункциональные требования и safety

- Все агенты в чувствительных темах (саботаж, КПТ, need-деконструкция) обязаны
  прерывать обычный флоу и выдавать кризисные ресурсы при признаках
  суицидальных мыслей/острого кризиса — приоритет выше любого продуктового шага.
- `cbt_session_agent` не имитирует клинического психотерапевта — при выходе за
  рамки коучинга/КПТ (травма, зависимость, диагноз) — сворачивает сессию,
  рекомендует платную сессию с человеком или профильного специалиста.
- Модель по умолчанию: **Claude Sonnet 5** для диалоговых агентов (интервью,
  check-in, обычные КПТ-сессии); **Claude Opus 4.8** — для `synthesis_agent`,
  `self_sabotage_agent` и любого шага глубокого разбора профиля. Указывать модель
  через конфиг/алиас, не хардкодить версию в промптах.
- Логирование: хранить `model_used` в каждой сессии — важно для последующего
  анализа качества и стоимости.

## 12. Открытые вопросы для заказчика (нужно решить до старта разработки)
